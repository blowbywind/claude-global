1. **조건부 실행 지시 → 즉시 실행 금지**: 메시지에 "확인 후/승인하면/검토 후/좋으면/이후에 진행/보고 나서" 등 승인 대기 표현이 있으면 실행하지 말고 계획만 제시 후 "실행 보류합니다. 승인 주시면 진행하겠습니다." 명시. 단 "X 계획 세워줘"처럼 현재 요청이 계획·정보 요청이면 바로 응답. (lessons 2026-06-07)
2. **파괴적 명령 제안 전 현재 상태 확인**: `rm -rf`·`DROP TABLE`·`git reset --hard` 및 `&&` 복합 명령은 상태 먼저 확인하고, 이미 완료됐으면 "재실행 금지" 명시. (lessons 2026-06-08)
3. **UI/구조 작업 전 실제 파일 확인**: CLAUDE.md Architecture를 신뢰하지 말고 `find`/`ls`로 실제 구조 확인. 파일 삭제·이동·추가 시 같은 커밋에서 Architecture 갱신(drift 방지). (lessons 2026-06-04)
4. **대형 파일·컨텍스트 관리**: `@파일멘션` 금지(경로 텍스트로 대체). 주제 전환·30턴 초과 시 새 세션 권장. 체감 100k 누적 시 `/compact` 수동 실행. (5,000줄/300KB 초과 Read는 hook이 자동 차단) (ADR 2026-06-10)
5. **memory/ 파일 추가 시 MEMORY.md 인덱스 한 줄 추가 필수** (`- [파일명](memory/파일명.md) — 설명`). 누락 시 미래 세션이 규칙을 못 찾음.
6. **백그라운드 HTTP 서버 금지**: VS Code 원격에서 `python3 -m http.server &` 등 금지, 검증은 `curl`로. (memory/feedback_background_server.md)
7. **Workflow 동시 에이전트 최대 3개**: `parallel()` 1회 4개+ 금지 → 세션 한도 초과로 전체 실패. 배치 분할 또는 `pipeline()` 사용. `agent()`는 null 반환 가능 → 항상 null 가드. (lessons 2026-06-11)
8. **/goal 토큰 절약**: 조건 텍스트 50단어 이내(Stop hook 평가마다 주입됨). Obsidian 프로젝트 노트 30줄 이하 유지. (lessons 2026-06-18)
9. **출력은 한국어만**: 상태 메시지·완료 보고·설명 전부 한국어 산문으로 작성. 일본어·중국어 혼용 금지는 물론 **영문 전체 응답도 금지**(코드 주석·커밋 메시지만 예외). 문장 안에 영문 기술 용어·코드 식별자 섞는 것은 허용하되 문장 자체는 한국어. (lessons 2026-06-11, 2026-07-08)
10. **hook 작업 규칙**: bash 글로브 차단 패턴은 이중 따옴표 내 `*` 그대로 사용(`\*`는 리터럴됨). hook 테스트는 `bash -n` 문법 검사로, 위험 문자열을 Bash로 직접 실행해 테스트 금지. active-rules 승격 항목엔 "(lessons 날짜)" 각주 유지(역추적).
11. **DB 스키마·데이터매핑 변경은 배포 전 검증**: ① sed/일괄 편집 시 "한 줄에 의미 다른 토큰이 섞였는지"(예: `HasColumnType`+`HasConversion` 동시 제거) 항목별 확인 ② 배포 전 code-reviewer 게이트 ③ 단위/일부 통합테스트 통과는 거짓양성 가능(빈 DB·일부 프로빙) → 실DB round-trip 값 검증. (lessons 2026-06-24)

12. **위임 결정 = 마커 즉시 출력 (절대 규칙)**: "위임합니다·roun에게 맡기겠습니다" 텍스트만 쓰고 `[[HANDOFF: botId | ...]]` 마커를 안 내면 위임은 실행되지 않는다. 위임 결정 즉시 마커를 응답 맨 끝에 출력하고 `]]`로 닫는다. 말과 마커가 동시에 나와야 위임이 실행됨. (lessons 2026-07-01)
13. **에이전트 보고 수신 후 재확인 루프 금지**: 에이전트 보고에 "빌드 통과·테스트 N개 통과" 결과가 명시됐으면 git log·WIP·파일 재확인 생략. 재확인이 필요한 경우는 보고에 결과가 없거나 실패 항목이 있을 때만. (lessons 2026-07-01)
14. **위임 전 전체 항목 한 번에 식별 → 1회 HANDOFF**: 소단위로 쪼개 반복 위임 금지. 위임 전 미완성 전체 목록을 먼저 파악하고, 같은 역할(roun=백엔드, arthur=프론트)에 해당하는 항목을 체크리스트로 묶어 1회 HANDOFF에 전달한다. 동일 봇에게 비슷한 잔여 작업을 반복 위임하면 자동 차단됨. (lessons 2026-07-01)
15. **시각/레이아웃 QA는 정적 규칙이 아닌 실제 렌더링 실측 필요**: "박스 밖으로 텍스트 이탈 금지" 같은 시각 규칙은 word-break·CSS 존재 여부 같은 정적 텍스트 검사로는 검증 불가 — 고정 height + 실제(특히 한글) 콘텐츠 조합에서만 드러남. HTML/PPTX 등 시각 산출물 QA 게이트를 설계·추가할 때는 반드시 렌더링 결과를 실측하는 단계를 포함할 것(웹은 헤드리스 브라우저의 `scrollHeight`/`clientHeight` 비교, PPTX는 도형 좌표 계산). 정적 검사만 있는 QA는 같은 레이아웃 버그를 테마가 바뀔 때마다 반복 통과시킨다. (lessons 2026-07-10)
16. **테마 변경 시 매개변수 치환 방식(색깔놀이) 금지 및 물리적 레이아웃 분리**: 사용자의 테마 다변화 요구 시, 동일한 뼈대 좌표 구조에 단순 색상/폰트/두께 등의 스타일 매개변수만 치환하여 여러 결과물을 만드는 방식을 금지한다. 테마별 고유 아이덴티티에 맞춰 배치 좌표, 컴포넌트 조합 구조, 그리드 분할수, 슬라이드 내 정보 흐름 위상을 70% 이상 다르게 설계하고 코드를 분기시켜야 한다. 기계적인 빌드 및 QA 통과(PASS) 여부만 확인하지 말고, 청중의 관점에서 완전히 차별화된 레이아웃인지 교차 시각 검토를 거쳐야 한다. (lessons 2026-07-10)
17. **디자인의 완성 기준 — 기획 의도와 트렌드 반영**: 디자인 QA 게이트(텍스트 잘림, 대비 충족 여부 등)를 통과하는 것은 준수해야 할 최소한의 기본 제약조건일 뿐, 그것이 디자인의 완성을 의미하지는 않는다. 디자인은 기획의 본질적 의도와 현재 트렌드를 모두 충족할 수 있도록 적절한 레이아웃, 풍부한 시각적 표현 및 독창적인 비주얼 아이덴티티를 내포하여 청중에게 가치를 전달할 수 있는 상태여야 한다. (lessons 2026-07-10)
